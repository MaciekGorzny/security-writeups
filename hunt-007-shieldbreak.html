HUNT-007 · Detection Engineering

ShieldBreak.exe: Cloud Filter ADS (Alternate Data Stream) bypass
i blind spot Sysmona

Próbka była testowana na Windows 11 VM w trzech sesjach, z dwóch lokalizacji na dysku. Sysmon złapał wyłącznie procesy Process Create i Process Terminate - zero zdarzeń plikowych, rejestrowych, sieciowych. Dopiero po uruchomieniu Procmona logi pokazały co faktycznie dzieje się w tych 150-300 ms: rejestracja Cloud Filter sync root, katalog w C:\, payload w alternatywnym strumieniu NTFS, parsowanie nagłówka PE i memory-mapped load. Brak elevacji. Brak sieci. Defender melduje "No threats found".

kontekst

PoC był testowany we własnym izolowanym DFIR labie (host-only VMware, broker MCP, brak NAT) zbudowanym przez Claude Code. Próbka pochodzi z repozytorium GitHub MSNightmare - ShieldBreak. Telemetria: Sysmon (live) + eksport Procmon CSV (ręczny) + surowe logi z drugiej sesji Sysmon.

kluczowy wynik

Bypass działa na Medium integrity level - nie wymaga elevacji ani żadnej modyfikacji konfiguracji Defendera. Próbka rejestruje się jako cloud provider przez oficjalne Windows API (Cloud Filter), tworzy ADS z wbudowanym payloadem (~2.4 MiB, stały rozmiar we wszystkich 12 uruchomieniach) i ładuje go przez memory-mapped I/O zamiast CreateProcess. Ładunek nigdy nie trafia na dysk jako .exe.

02 Co faktycznie robi proba

Wzorzec identyczny w kazdym z 10 uruchomien złapanych przez Procmon. Ponizej pelna sekwencja dla jednego runa (PID 2132, 13:31:40 CEST). Tylko elementy wnoszone przez probe - szum Procmona (LoadImage systemowych DLL, SRP/SmartLocker registry queries) pominieto.

Krok 1 - rejestracja Cloud Filter sync root

1
procmon: regsetvalue / createfile

Proba wywoluje CfRegisterSyncRoot (Cloud Filter API, cldapi.dll). Windows zapisuje wpis sync root do HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Explorer\SyncRootManager\ShieldBreak!... i tworzy katalog C:\ShieldBreak_{GUID} z atrybutem Hidden. GUID generowany losowo przy kazdym uruchomieniu, format identyczny.

Krok 2 - staging payloadu w ADS

2
procmon: createfile

Otwarcie alternatywnego strumienia danych: C:\ShieldBreak_{GUID}\BERLIN:stream, Disposition: OverwriteIf. Strumien jest nazywany BERLIN i umieszczony wewnatrz pliku BERLIN w ukrytym katalogu.

2b
procmon: setendoffileinformationfile

Rezerwacja rozmiaru: EndOfFile: 2 517 928 B (dokładnie ~2.4 MiB, ten sam rozmiar w kazdym z 10 uruchomien - payload jest statyczny, nie pobierany z sieci).

Krok 3 - parsowanie naglowka PE

3
procmon: readfile x3

Trzy odczyty ze strumienia w kolejnosci:

  • offset 0, dlugosc 2 - podpis MZ
  • offset 60, dlugosc 4 - pole e_lfanew w IMAGE_DOS_HEADER
  • offset 224, dlugosc 4 - pole w IMAGE_NT_HEADERS

Klasyczna sekwencja parsowania naglowka PE przez reflective loader. Proba weryfikuje ze payload ma prawidlowy format przed zaladowaniem.

Krok 4 - reflective load przez memory-mapped I/O

4
procmon: createfilemapping

CreateFileMapping na strumieniu BERLIN z PageProtection: PAGE_READONLY. Strumien mapowany do pamieci procesu. Brak CreateProcess, brak Load Image dla payloadu - z perspektywy Sysmona proces robi "nic" przez te 150-300 ms i konczy sie z kodem 0.

uwaga

Zawartosc payloadu (~2.4 MiB) nie byla analizowana w tej sesji - nie wiadomo czy zostal wykonany i co robi. Udało się jedynie potwierdzić że jest to prawidlowy PE (naglowek parsuje sie poprawnie) i ze Defender go nie wykrywa (No threats found na ntdll.dll uzyty jako payload testowy w screenshocie z konsoli). Analiza payloadu to osobny krok.

03 Dlaczego Sysmon tego nie widzi

Znaleziono dwie niezalezne przyczyny nakladajace sie na siebie. Obie zostały potwierdzone w pliku konfiguracyjnym laba (sysmon-config-lab.xml).

PrzyczynaEfekt
Brak sekcji <FileCreateStreamHash> (EID 15) w konfiguracji Sysmon strukturalnie nie generuje zadnego zdarzenia dla zapisu do ADS. To nie jest filtr - kategoria w ogole nie jest wlaczona. Właczenie EID 11 (FileCreate) nie pomaga, bo EID 15 to osobna kategoria dedykowana dla strumieni.
Istniejaca regula FileCreate catch-all zawierała warunek TargetFilename condition="contains" "." Sciezka C:\ShieldBreak_{GUID}\BERLIN:stream natomiast nie zawiera zadnej kropki. Nawet gdyby EID 15 byl wlaczony, ten konkretny wzorzec nazwy ominąłby regułę.

Pierwsze uruchomienia (PIDs 5808-12472, sesja 13:30-15:44 CEST) mialy aktywnego Procmona i dlatego widac je w CSV. Ostatnie dwa (PID 3356 i 6340, 17:24 i 17:42) były uruchomione recznie z pulpitu i Sysmon również je zlapał - ale tylko Process Create/Terminate, nic poza tym, z tego samego powodu.

Zalecana latka konfiguracji

Dwie zmiany do sysmon-config-lab.xml, zgodnie z zasada braku hardeningu - zapisane jako obserwacja, nie wdrozone automatycznie:

<!-- 1. Nowa sekcja dla ADS - dedykowane zdarzenie Sysmona -->
<FileCreateStreamHash onmatch="include">
  <Rule name="ads_write" groupRelation="or">
    <!-- laplemy wszystkie zapisy do strumieni na C:\ -->
    <TargetFilename condition="begin with">C:\</TargetFilename>
  </Rule>
</FileCreateStreamHash>

<!-- 2. Uzupełnienie istniejącej reguły FileCreate -->
<FileCreate onmatch="include">
  <!-- istniejaca regula (z wymogiem kropki) -->
  <Rule name="file_create_ext" groupRelation="or">
    <TargetFilename condition="contains">.</TargetFilename>
  </Rule>
  <!-- nowy wariant: pliki/katalogi tworzone bezposrednio w korzeniu -->
  <Rule name="file_create_root_c" groupRelation="or">
    <TargetFilename condition="begin with">C:\ShieldBreak</TargetFilename>
  </Rule>
</FileCreate>

Wariant file_create_root_c jest celowo zaweżony do wzorca C:\ShieldBreak - szersza reguła "wszystko w C:\" byłaby słusznie odrzucona jako zalew szumu. Po potwierdzeniu że proba zawsze uzwa tego prefiksu, zawężenie jest bezpieczne i zerokosztowe.

04 Sygnaly detekcyjne - MDE Advanced Hunting

Ponizej reguly niezalezne od nazwy pliku - żadna nie opiera sie na "ShieldBreak" w sciezce.

Regula 1 - rejestracja sync root poza zaufanymi cloud providerami

// SyncRootManager: Cloud Filter - rejestracja sync root przez proces
// ktory nie jest zadnym ze znanych providerow (OneDrive, iCloud, Dropbox, Box)
// FP: nowe legalne aplikacje cloud - wymaga whitelistowania po baseline
DeviceRegistryEvents
| where ActionType == "RegistryKeyCreated"
| where RegistryKey has "SyncRootManager"
| where not (RegistryKey has_any (
    "OneDrive", "SharePoint", "iCloud",
    "Dropbox", "Box", "GoogleDrive", "Nextcloud"
))
| project Timestamp, DeviceName, InitiatingProcessFileName,
          InitiatingProcessFolderPath, RegistryKey

Regula 2 - ADS write przez podejrzany proces

// Zapis do alternatywnego strumienia danych (dwukropek w nazwie pliku)
// Wyklucza typowe legalne ADS: Zone.Identifier, SmartScreen, Afp_AfpInfo
// Wymaga: MDE DeviceFileEvents z FileCreated/FileModified
DeviceFileEvents
| where ActionType in ("FileCreated", "FileModified")
| where FileName has ":"
| where not (FileName has_any (
    "Zone.Identifier", "Afp_AfpInfo",
    "SummaryInformation", "DocumentSummaryInformation"
))
// Opcjonalny filtr: tylko ADS w korzeniu dysku
| where FolderPath matches regex @"^[A-Za-z]:\\\\"
| project Timestamp, DeviceName, FolderPath, FileName,
          InitiatingProcessFileName, InitiatingProcessFolderPath, SHA256

Regula 3 - korelacja DLL: cldapi.dll + fltLib.dll z nieoczekiwanej lokacji

// Jeden proces laduje jednoczesnie Cloud Filter API i Filter Manager client
// spoza System32/OneDrive - kombinacja nie wystepuje u zadnego legalnego procesu
// Zero FP w typowym srodowisku korporacyjnym
DeviceImageLoadEvents
| where FileName in ("cldapi.dll", "fltLib.dll")
| where InitiatingProcessFolderPath !contains @"Windows\System32"
| where InitiatingProcessFolderPath !contains "OneDrive"
| where InitiatingProcessFolderPath !contains "Defender"
| summarize
    dlls = make_set(FileName),
    folders = make_set(InitiatingProcessFolderPath)
    by InitiatingProcessId, InitiatingProcessFileName,
       DeviceName, bin(Timestamp, 30s)
| where set_has_element(dlls, "cldapi.dll")
    and set_has_element(dlls, "fltLib.dll")

Regula 4 - MpClient.dll ladowany spoza Defendera

// MpClient.dll powinna ladowac wylacznie MsMpEng i SecurityHealthService
// Kazdy inny proces to anomalia - dotyczy tez potencjalnych wersji probe z inna nazwa
DeviceImageLoadEvents
| where FileName == "MpClient.dll"
| where InitiatingProcessFileName !in~ (
    "MsMpEng.exe", "SecurityHealthService.exe",
    "MpDefenderCoreService.exe", "msmpeng.exe"
)
| where InitiatingProcessFolderPath !contains "Windows Defender"
| project Timestamp, DeviceName, InitiatingProcessFileName,
          InitiatingProcessFolderPath, InitiatingProcessSHA256

Regula 5 - Sysmon EID 1: brak metadanych PE + Medium IL (sygnał wspomagający)

// Standalone: za duzo FP zeby uzywac samodzielnie
// Jako korelacja z regula 1/2/3 w oknie 60s: wysokie zaufanie
Event
| where Source == "Microsoft-Windows-Sysmon" and EventID == 1
| extend
    Image          = tostring(EventData.Image),
    FileVersion    = tostring(EventData.FileVersion),
    Description    = tostring(EventData.Description),
    Company        = tostring(EventData.Company),
    IntegrityLevel = tostring(EventData.IntegrityLevel),
    ParentImage    = tostring(EventData.ParentImage)
| where FileVersion == "-" and Description == "-" and Company == "-"
| where IntegrityLevel == "Medium"
| where Image !contains @"WindowsApps\"
| where Image !contains @"Windows\System32\"
| where Image !contains @"Windows\SysWOW64\"
| where Image !contains @"Program Files\"
| project TimeGenerated, Computer, Image,
          ParentImage, IntegrityLevel
zalecenie wdrozenia

Reguly 2 i 3 nadaja sie do staged rollout (najpierw alert-only, tydzien baselining). Regula 1 wymaga whitelisty cloud providerow wlasciwej dla środowiska przed wdrożeniem. Reguła 4 jest gotowa do wdrozenia bez tuningu - MpClient.dll poza Defenderem to anomalia bez znanych legalnych wyjątkow.

Sysmon EID 15 (po wdrozeniu latki konfiguracji)

// Uzywac PO wdrozeniu FileCreateStreamHash w konfiguracji Sysmona
// Lapie kazdy zapis do ADS ktory nie jest Zone.Identifier
Event
| where Source == "Microsoft-Windows-Sysmon" and EventID == 15
| extend TargetFilename = tostring(EventData.TargetFilename)
| where TargetFilename !has "Zone.Identifier"
| where TargetFilename !has "SummaryInformation"
| project TimeGenerated, Computer, TargetFilename,
          tostring(EventData.Image), tostring(EventData.Hash)

05 YARA

rule ShieldBreak_CloudFilter_ADS_Bypass
{
    meta:
        description = "Cloud Filter API + Object Manager symlink chain - Defender ADS bypass"
        author      = "Maciej Gorzny"
        date        = "2026-08-13"
        reference   = "maciekgorzny.github.io/security-writeups/hunt-007"
        tlp         = "WHITE"

    strings:
        // Object Manager namespace - strukturalne, nie kosmetyczne
        $om_target = "WD_TARGET_"  ascii wide
        $om_shadow = "WD_SHADOW_"  ascii wide
        $om_scan   = "WD_SCAN"     ascii wide

        // Sciezka triggera skanu przez globalroot
        $globalroot = "globalroot"  ascii wide nocase

        // Komponent ADS - stala nazwa strumienia
        $berlin     = "BERLIN"      ascii wide

        // Cloud Filter API imports - bez tych funkcji mechanizm nie dziala
        $cf1 = "CfRegisterSyncRoot"   ascii
        $cf2 = "CfCreatePlaceholders" ascii
        $cf3 = "CfConnectSyncRoot"    ascii

    condition:
        uint16(0) == 0x5A4D  // MZ header
        and (
            // Wysokie zaufanie: Object Manager namespace + globalroot
            ( ($om_target or $om_shadow) and $om_scan and $globalroot )
            or
            // Wysokie zaufanie: Cloud Filter imports + WD namespace
            ( any of ($cf*) and ($om_target or $om_shadow) )
            or
            // Srednie: stala nazwa ADS + scan namespace
            ( $berlin and $om_scan and $globalroot )
        )
}

Regula nie zawiera hash'a - opiera sie wylacznie na logice programu. Przekompilowanie PoC ze zmienionymi nazwami zmiennych pominie reguly sygnaturowe, ale nie te.

08 Otwarte watki

  • Zawartosc payloadu (2 517 928 B) nie została zdekompilowana i nie wiadomo co faktycznie wykonuje - jest to priorytetem do nastepnej sesji.
  • Uruchomienia PID 2860 i 12768 (16:00-16:01 CEST) nie pojawiły sie w żadnych logach Sysmona mimo że process_creation rule powinna je złapać - może się to wiazac z przerwą w danych miedzy 15:13-15:14 UTC w tym eksporcie.
  • Regula YARA nie została przetestowana na wariantach z innymi nazwami przestrzeni Object Manager - może być podatna na zmianę nazwy.
  • Regula MDE dla SyncRootManager nie baselinowana na środowisku produkcyjnym - nieznana jest liczba FP z legalnych cloud sync aplikacji.
