Zautomatyzowany lab DFIR: pierwszy test na legacyhive.exe

Ten sam sampl przeszedł przez dwie niezależne ścieżki analizy - statyczną (REMnux) i dynamiczną (Sysmon + Procmon na Windows 11) - w izolowanym labie, którym w całości sterował Claude przez własny broker MCP. Statyka nic nie wykazała. Dynamika, dopiero po dodaniu Procmona, ujawniła pełny łańcuch: edycję hive'a w pamięci i proces odpalony pod cudzą tożsamością.

breakthrough

Cztery nieudane próby, na dwóch osobnych buildach VM, zanim znaleziono przyczynę: pierwszy argument (username), a nie trzeci (target_user_hive, zgodnie z usage stringiem), decyduje którego hive'a narzędzie faktycznie otwiera i nadpisuje. Wszystkie wcześniejsze uruchomienia podawały jako argument pierwszy konto brokera - aktywnie zalogowane na konsoli - więc próbka za każdym razem zderzała się z własną blokadą sesji, zanim dotarła do realnej logiki.

01 Architektura laba

Broker (mój laptop) ma dwa interfejsy: jeden do internetu (rozmowa z Claude), drugi do segmentu host-only VMware bez NAT, gateway i DNS. VM-ki nigdy nie łączą się z internetem, nawet pośrednio. Kierunek połączeń jest zawsze broker → VM. Serwer MCP odpalany jest ręcznie, tylko na czas sesji testowej - nie jako stała usługa.

Trzy niezależne procesy MCP, po jednym na moduł, celowo nigdy nie łączone ze sobą ani z osobnym, niepowiązanym blue-team-mcp (narzędzia offensive/defensive z CTF-a):

ModułCelTransport / źródło telemetrii
telemetry/Linux VMSSH + bash, auditd / ausearch
windows/Windows 11 VMSSH + PowerShell, Sysmon / Get-WinEvent, później Procmon
static/REMnux VMSSH + bash, brak sieci na VM - hash_lookup jako jedyny wyjątek działa z brokera

Powód rozdzielenia Windows od Linuksa zamiast jednego brokera z parametrem os=: zupełnie inny transport (PowerShell vs bash) i inne źródło telemetrii (Sysmon vs auditd) - wspólny proces oznaczałby rozgałęzianie po OS-ie wszędzie w kodzie, który poza tym jest generyczny.

twarda zasada

Brak hardeningu VM. Lab ma pokazywać, jak próbki/techniki faktycznie zachowują się na czystym, niehardenowanym systemie - dopisywanie reguł do local_rules.xml stłumiłoby albo zmieniło dokładnie to zachowanie, które lab ma uchwycić. Narzędzia raportują luki; nie łatają ich.

Co faktycznie zrobił udany run - 5 kroków

1
procmon: load image

Load offreg.dll. Próbuje najpierw katalogu własnego (nie znaleziono), potem ładuje Offline Registry API z C:\Windows\System32\offreg.dll.

2
procmon: createfile / readfile

Otwarcie docelowego hive'a. CreateFile na NTUSER.DAT konta User2, Generic Read. Udaje się wyłącznie dlatego, że User2 jest wylogowany.

3
brak telemetrii - z natury API

Edycja wartości hive'a w pamięci. OFFREG parsuje hive do struktury w procesie i mutuje ją tam. Żaden WriteFile, RegSetValue ani inne I/O nie odpowiada temu krokowi - jedyny fragment tej techniki bez śladu w żadnym źródle telemetrii.

4
procmon: writefile ×~210, setrenameinformationfile

Zapis i atomowa podmiana. Przepisany hive strumieniowany do pliku tymczasowego w folderze o nazwie GUID, potem SetRenameInformationFile (ReplaceIfExists) podmienia go nad oryginałem - ten sam wzorzec powtórzony dla UsrClass.dat.

5
sysmon: process create (event id 1)

Odpalenie procesu jako impersonowany użytkownik. 7 sekund później C:\Windows\notepad.exe startuje jako dziecko legacyhive.exe - ale pod tokenem User2, nie Admina. To jest właściwy payload PoC: pełna impersonacja tożsamości docelowego konta.

05 Finding istotny dla detekcji

detection-relevant

Proces potomny, którego pole User różni się od konta właściciela procesu rodzica, to gotowy kształt reguły korelacyjnej - Sysmon sam z siebie tego nie flaguje, ale ParentUser ≠ User na Process Create jest tanim, nisko-szumowym sygnałem. Zgodnie z zasadą "brak hardeningu" w tym labie, zapisane jako obserwacja, nie wdrożone jako reguła w local_rules.xml.

06 Realne błędy znalezione przy budowie tooling'u

Wartość dla kogoś budującego podobny broker - te błędy nie były oczywiste z dokumentacji.

Linux (auditd)

  • ausearch czyta pusty stdin zamiast pliku logu przy wywołaniu przez sesję SSH bez TTY - wymaga --input-logs.
  • ausearch -ts/-te na auditd 3.1.2 nie akceptują @epoch ani pojedynczego cytowanego stringa daty - trzeba dwóch osobnych, sformatowanych lokalnie tokenów (date -d @epoch '+%x %X'), generowanych na samej VM, żeby ominąć niezgodność locale broker/VM (en_US vs pl_PL).
  • ausearch zwraca kod wyjścia 1 przy <no matches> - to normalny wynik, nie błąd.

Windows (Sysmon + Procmon)

  • Klucz rejestru DefaultShell OpenSSH cicho nie działa - każda komenda jawnie wywołuje powershell -NoProfile -NonInteractive -EncodedCommand <base64 UTF-16LE>.
  • Limit 8191 znaków linii poleceń cmd.exe psuje duże payloady -EncodedCommand (np. pełne XML konfiguracji Sysmona) - transfer plików przeniesiony na SFTP.
  • sftp używa -P (wielkie) dla portu, nie -p (to "zachowaj atrybuty").
  • sftp -b (batch mode) cicho ustawia BatchMode=yes, co zabija autentykację przez hasło - naprawione jawnym -o BatchMode=no.
  • Kod wyjścia sysmon.exe przez PowerShell jest niewiarygodny (NativeCommandError potrafi ustawić niezerowy kod nawet przy realnym sukcesie) - configure_profile ocenia sukces na podstawie treści outputu, nie kodu wyjścia.
  • Output konsolowy sysmon.exe to UTF-16 nawet po przekierowaniu - pojawia się jako bajty null, jeśli się ich nie usunie.

Procmon - najtrudniejsze błędy do złapania (ciche zawieszenia, nie wyjątki)

  • /Terminate w PsExec wraca zaraz po wysłaniu sygnału stop - ale oryginalny proces Procmon (trzymający .pml) potrzebuje jeszcze kilku sekund na realny flush i wyjście. Odpalenie kolejnej komendy Procmon zanim ten poprzedni proces faktycznie zniknie nie daje błędu - nowe wywołanie po prostu wisi w nieskończoność, Responding=True, zero outputu. Naprawione twardym pollingiem (_wait_for_no_procmon_process) przed każdym kolejnym wywołaniem.
  • Świeżo utworzony .pml/.csv może legalnie mieć 0 bajtów przez jeden-dwa polle, zanim Procmon zacznie faktycznie pisać - wczesna wersja pollingu stabilności pliku traktowała dwa kolejne odczyty 0-bajtowe jako "stabilne" i zwracała ścieżkę do pustego pliku. Naprawione: 0 bajtów nigdy nie jest traktowane jako stabilne.
  • Procmon to prawdziwa aplikacja GUI (w przeciwieństwie do Sysmona, usługi z driverem) - potrzebuje interaktywnej stacji okien. Automatyzacja SSH działa w Session 0 (sesja usług), bez żadnego interaktywnego logowania. Rozwiązanie: PsExec64.exe -accepteula -i <session_id> -d Procmon64.exe …, wstrzyknięcie do konkretnej, już zalogowanej sesji interaktywnej (znalezionej przez quser).

REMnux

  • 5 z 10 domyślnych plików reguł YARA zależy od modułu manape skompilowanego tylko w opatchowanym buildzie YARA używanym przez manalyze - realne ograniczenie środowiska, obsłużone per-plik, żeby jedna zła reguła nie przerywała całego skanu.
  • hash_lookup to jedyne narzędzie uruchamiane z brokera, nie z VM - REMnux jest odcięty od sieci, VirusTotal wymaga internetu, więc z izolowanego segmentu wychodzi tylko hash, nigdy sam sampl.

07 Wazuh - powracający ból głowy

Wazuh spowodował więcej pracy diagnostycznej na samym labie niż jakikolwiek testowany cel. Dwa oddzielne epizody niestabilności managera (10.0.0.129) w jednej sesji:

  1. Twardy OOM-kill - szczyt 15.7GB RSS na VM z 19GB RAM.
  2. "Ciche zatrzymanie" - wazuh-analysisd żył dalej, ale przestał produkować nowe alerty przez ~8 minut mimo realnej telemetrii, pamięć wracała ku 12.5GB, plus bezsensowna linia loga (Total rules enabled: 387864150).

Oba rozwiązane restartem wazuh-manager; RAM VM podniesiony 19GB → 31GB. Lekcja wpisana do dokumentacji modułu: jeśli get_wazuh_alerts/diff_raw_vs_alerted nagle zwracają podejrzanie pusto mimo realnej aktywności - sprawdź free -h i systemctl status wazuh-manager na managerze, zanim założysz błąd brokera.

Po stronie Windows problemy z łącznością agenta (nieaktualne IP po re-klonowaniu VM itd.) powtarzały się na tyle, że po przebudowie Windows VM od zera padła decyzja, żeby w ogóle nie podłączać agenta Wazuh do nowej Windows VM. Blok konfiguracji wazuh_manager zostaje w windows/config.yaml dla agenta Linux, ale get_wazuh_alerts/diff_raw_vs_alerted dla modułu Windows odtąd zawsze zwracają zero - to oczekiwane, nie bug. get_raw_telemetry (prosto z kanału zdarzeń Sysmon, bez zależności od Wazuha) stał się jedynym źródłem telemetrii dla tego modułu.

08 Otwarte wątki

  • Rzeczywiste przeznaczenie trzeciego argumentu legacyhive.exe pozostaje nieznane - nigdy nie zaobserwowano jego odczytu w żadnym runie.
  • Czy nowy build Windows VM zmienia zachowanie legacyhive.exe wobec innego konta docelowego lub innego kontekstu uprawnień - nietestowane.
  • local_rules.xml dla luki auditd na Linuksie (§01) pozostaje celowo niedopisane.
  • Trzy nowe tool'e Procmon zostały przetestowane bezpośrednio przez wywołania modułu, jeszcze nie przez żywą listę tooli MCP - działający proces servera powstał przed tą zmianą kodu i wymaga restartu Claude Code, żeby podjąć je jako pełnoprawne tool'e.
